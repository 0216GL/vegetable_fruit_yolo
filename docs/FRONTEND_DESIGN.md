## 二、功能范围

**一条核心链路，两个表面。**

```
拍照 ──▶ 上传 ──▶ 看结果 ──▶ 存进历史
```

### 完整页面清单

**五个页面，全部已经写完了。** 只看到两个是因为另外三个没有明显入口。

| # | 页面 | 路由 | 依赖的后端接口 | 状态 |
|---|---|---|---|---|
| 1 | 上传 | `/h5` | `POST /inspection/predict` | ✅ 已完成，能跑 |
| 2 | 结果 | `/h5/result` | 同上 | ✅ 已完成，能跑 |
| 3 | 历史列表 | `/h5/history` | `GET /inspection/list` | ✅ 代码完成，**等 P2** |
| 4 | 大屏 | `/screen` | `GET /stats/overview` | ✅ 代码完成，**等 P4** |
| 5 | 令牌自检 | `/dev/tokens` | 无 | ✅ 开发用，上线删 |

### 有一个"看起来需要新页面"其实不需要

「点历史记录进去看某一次的详情」看起来要第 6 个页面。

其实不用 —— **结果页本来就是"渲染一次识别结果"**。给它加一个可选的 `id` 参数就够了：

- 不传 `id` → 读内存里的最近一次（上传完直接跳过来的场景）
- 传 `id` → 从接口拉那条历史记录

**一份组件，两种入口。** 新开一个页面等于把标注图、色带、逐果清单全部复制一遍，
以后改一处就得改两处。这是前端最常见的自我膨胀方式。

### 登录：一个需要你拍板的取舍

登录**不在当前范围里**（是被明确砍掉的，见 `PRODUCT.md`）。但你想清楚了要加，也可以。

**它花的不是"一点时间"，是一整条链路：**

| 后端要做 | 前端要做 |
|---|---|
| 用户表 + 密码哈希（BCrypt） | 登录页 |
| JWT 签发与校验 | token 存储 |
| 拦截器给每个接口加鉴权 | 请求拦截器挂 token |
| Redis 存作废 token | 路由守卫 |
| 退出登录 | 401 统一处理 |

工作量大约是现在**整个前端的二分之一**。

**它换来的：** 答辩时"多人怎么用"有答案；简历上多一个 JWT 实战点。

**它挤掉的：** 你是单人在做。这些时间本来可以用来把算法讲透、把演示做顺 ——
而那两件事才是真正拿分的。

**建议：现在不做。** 但 `api/request.js` 里已经留好了挂 token 的位置和注释，
真要做也不返工。

**另外要澄清一个因果关系：** 就算决定要做，也确实只能等后端 P3 做完 ——
登录页没法对着不存在的接口开发。所以这不是"等不等"的问题，是"要不要"的问题。

### 统计从哪来

**大屏就是统计视图**，不需要另开页面。口径要在答辩时讲得清楚：

| 指标 | 口径 | 备注 |
|---|---|---|
| 可采收率 | 着色期及以上 ÷ 总检出数 | ⚠️ 门槛是**待确认的业务规则**，不是农业标准 |
| 分布 | 四个等级的计数 | 数据来自已有接口 |
| 趋势 | 按天聚合历史记录 | 需要 `charts`，见下 |

**趋势图是唯一需要引图表库的地方**（ECharts 约 1MB）。要不要上，你定：
它对路演观感有帮助，但需要 P2+P4 的数据才画得出东西。

另外**历史页顶部可以加一条汇总**（本周巡检次数、平均可采收率）——
成本极低，能让历史页不像一个空列表。建议做。

### 其他功能：做 / 不做

| 功能 | 结论 | 理由 |
|---|---|---|
| **摄像头实时识别** | 建议做，但排在大屏之后 | 路演现场"举起手机就认"比上传照片震撼得多。复用同一个 `/predict` 接口，前端一个页面的活 |
| 历史页顶部汇总条 | 建议做 | 成本极低，观感提升明显 |
| 导出 CSV | 可选 | 合作社场景有用，但对评委无感 |
| 多次巡检对比 | 不做 | 要选两条记录做 diff，复杂度高、收益低 |
| 地块管理 | 不做 | 已明确砍掉，地块只是文本标签 |
| 角色权限 | 不做 | 同上 |
| 病虫害识别 | 不做 | 数据不可得（柿果源图已丢失） |
| 国际化 / 明暗主题切换 | 不做 | 场景不需要 |
| 图片存 OSS | 不做 | 存本地够用 |

### ★ 真正的结论：前端不缺页面，缺数据

这是一个容易看反的地方。

现在五个页面里，**三个是"代码写完了但没东西可显示"** —— 不是页面不够，是数据不通。
历史页显示"记录功能还没上线"，大屏显示"还没有巡检数据"，都是这个原因。

**而它们要的不是"整个后端"，只是一小块：把一次巡检结果存进数据库、再查出来。**

```
需要后端做的（按顺序）：

  ① 巡检结果落库 + 一个列表查询接口   ← 只要这一块，历史页和大屏就活了
  ② 统计聚合接口                      ← 大屏的数字变成真的
  ③（可选）登录                        ← 目前不做

  Python AI 服务已经好了，不用动。
```

**做完 ① 和 ②，这就是一个完整闭环**：拍照 → 识别 → 存档 → 看板。
不需要登录，不需要权限，不需要微服务。

## 三、技术栈

Vue 3（组合式 API）+ Vite + Vue Router 4 + Pinia + axios + ECharts，**JavaScript**。

组件库 **Element Plus，但只用于管道件**（table / form / dialog / message）。
颜色、圆角、阴影全部覆盖成自有令牌。**逐果标注图和成熟度色带手写。**

图标：`@element-plus/icons-vue` 一个家族，够用，不额外引依赖。
（taste-skill 和 ui-ux-pro-max 都禁止用 emoji 当图标。）

## 五、设计令牌（两级架构）

这是最能体现「企业规范感」的一处，来自 ui-ux-pro-max 的令牌架构。

**规矩：组件里不允许出现十六进制色值。** 只能用语义令牌。
（ui-ux-pro-max 第 6 类把 `Raw hex in components` 直接列为反模式。）

### 第一级：原始令牌（`primitives.css`）

只有值，不含用途。

```css
--hue-unripe:   #93A83F;   /* 青黄 */
--hue-turning:  #D6B23C;   /* 金黄 */
--hue-coloring: #E07B33;   /* 橙   */
--hue-full:     #B5372A;   /* 深红 */
--paper:        #F2F4EE;   /* 极浅绿白 */
--ink:          #1A1F16;
--ink-2:        #5C6653;
--rule:         #DDE3D5;
```

**四个成熟度色的来源：** 取自模型实测的色相顺序
（未熟 62.7° → 转色期 53.2° → 着色期 35.6° → 完熟 29.5°，见 `README.md`）。
界面上做了**拉开处理**以保证可区分——原始色相里相邻两级只差 6°，会糊成一片。

### 第二级：语义令牌（`semantic.css`）

描述用途，界面只读这一层。

```css
--color-surface:        var(--paper);
--color-text-primary:   var(--ink);
--color-text-secondary: var(--ink-2);   /* 从底色色相派生，不用中性灰 */
--color-border:         var(--rule);
--color-ripeness-1:     var(--hue-unripe);
/* ... 2/3/4 同理 */
```

**为什么非要做两级：** 以后要加深色大屏、要调整品牌色，只改 `primitives.css` 一处，
组件一行不动。这就是令牌架构存在的理由。

## 七、成熟度色带：一个必须处理的问题

成熟度靠颜色区分，但 **ui-ux-pro-max 第 10 类明确把「只靠颜色传达信息」列为反模式**。
而且柿果的「着色期（橙）」和「完熟（深红）」对色觉障碍用户本来就难分。

**处理办法：三重编码，颜色只是其中一层。**

```
▓▓▓▓▓▓▓▓▓▓▒▒▒▒▒▒▒▒▓▓▓▓▓▓▓▓▓▓░░░░░░░░
未熟 34     转色期 22    着色期 41    完熟 18
  1           2            3           4
```

色块 + **中文名称** + **数量**，三者同时出现。任何一层缺失都不影响理解。
逐果清单里同理：每个框旁边是「着色期 90%」，不是只有一个颜色。

**答辩时这就是一个能讲的技术点：** 颜色是这个产品的核心信号，
所以更要防止界面退化成"只有颜色能读懂"。

## 八、状态清单（「不像作业」主要靠这个）

多数学生项目只做「成功状态」。企业规范要求把边界状态都做出来。

| 状态 | H5 上传页 | 结果页 |
|---|---|---|
| 默认 | 拍照按钮 + 说明 | — |
| 加载中 | 上传进度（**不用转圈，用骨架/进度条**） | 标注框逐个画入 |
| 空 | — | 「这张图里没找到柿子」+ 引导重拍 |
| 错误 | 「图片太大了，请压缩后再传」 | 「识别服务没响应，稍后重试」 |
| 失败重试 | 重试按钮 | 重试按钮 |

**错误文案的规矩**（impeccable `craft-floor`）：说清**问题是什么**和**怎么补救**，
不道歉、不含糊。「网络错误」是坏文案；「识别服务没响应，请稍后重试」是好文案。

## 九、动效：只做一个

结果出现时那一次编排：照片淡入 → 检测框**按顺序逐个画入**（每个错开 60ms）→ 色带填充。

**只做一个的理由**（impeccable `craft-floor`）："每个区块都 fade-and-slide-up、
每张卡片都 hover 动一下"是 AI 生成的典型特征。一个精心编排的瞬间更有分量。

而且它有信息量：展示了"AI 正在逐个识别果实"这个过程。

**规矩：** 只动 `transform` 和 `opacity`，不动 `width`/`height`；
必须尊重 `prefers-reduced-motion`（关掉动画时直接显示最终状态）。

## 十、别漏了「浏览器自带的那些部分」

impeccable `craft-floor` 的原话：**"这是判断一个页面是被建造的、还是被拼装的，
最便宜的信号，也是模型最稳定会漏的一条。"**

在 `base.css` 里统一处理：

- 文字选中色（`::selection`）
- 焦点环（`:focus-visible`）——**不能删，只能改好看**
- 滚动条
- 表格里的数字用 `font-variant-numeric: tabular-nums`（数字等宽，不跳动）
- 下划线的偏移量
