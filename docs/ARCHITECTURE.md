## 一、项目定位

**一句话：** 面向柿果种植的 AI 巡检平台 —— 果农用手机拍一张照上传，平台自动**定位每一颗果实**、**判断成熟度**，汇总成"这块地现在能不能采、大概能采多少"的采收决策依据。

**为什么是这个场景（路演要讲的故事）：**

柿果是**呼吸跃变型**果实，成熟度不一致。传统做法是靠老师傅看颜色凭经验判断，问题是两头都亏：

- 采早了 → 涩、脱涩难、卖不上价
- 采晚了 → 落果、软烂、损耗大

而且柿果**同一棵树上不同果实的成熟度能差好几级**，只看整片林子"大概熟了"没有用，必须精确到单果。

现有方案要么靠人（贵、慢、不一致），要么靠大型分选线（几十万一台，小农户用不起）。这个平台的定位是**零硬件成本的软件方案**：用手机拍照 + 云端 AI，把"单果级成熟度判断"这件事的门槛降到一部手机。

**技术上的真正难点**（答辩时这是加分的点，别说"就是调了个 YOLO"）：

- **成熟度是连续量，不是离散类别**。着色期与完熟期果实的平均色相只差 6°，这在国际公开数据集里几乎没有标注规范，标注本身就是难点。
- **颜色信号极其脆弱**。而 YOLO 默认的数据增强 `hsv_s=0.7`（饱和度随机抖动 ±70%）恰好会摧毁这个信号 —— 这是本项目实测踩到的最大坑，也是区别于"随便找个教程跑个 demo"的地方。
- **模型的"自信"不可靠**。实测发现柿果模型判错时的平均置信度高达 82%，说明 softmax 过度自信，加拒识阈值反而降低整体准确率。这个结论和物种模型完全相反。

## 三、关键设计决策（答辩必问，每条都要能答上来）

### 1. 为什么拆成 Java 和 Python 两个服务，不合成一个？

| | Java 服务 | Python 服务 |
|---|---|---|
| 负责 | 用户、权限、业务规则、事务、统计 | 模型推理 |
| 换掉它会有多麻烦 | 业务逻辑重写 | 换模型/换框架，业务代码一行不动 |

**理由：** 两边生态不可替代。AI 生态在 Python（PyTorch / Ultralytics），企业级后端生态在 Java（Spring 的事务、权限、生态组件）。硬要合成一个，要么用 Java 调 Python（JNI/ONNX，工程上很痛），要么用 Python 写业务（团队协作、招聘都吃亏）。

拆开之后有一条**很硬的收益**：模型迭代和业务迭代解耦。以后模型从 YOLO11n 换成别的、或者加病虫害识别，只要 `/api/predict` 的返回结构不变，Java 侧一个字都不用改。

**不这样会怎样：** 模型一升级就得动业务代码，两拨人互相阻塞。

#### 这不是"没办法的将就"，是行业标准做法

大厂的典型分工是：**算法团队**把模型部署成一个独立的推理服务，**业务团队**负责调它。两边是不同的人、不同的技术栈，中间靠一份**接口契约**对接。

本项目里，那份契约就是 `ai/server/schemas.py` 和 `persimmon/src/main/java/org/ymg/persimmon/ai/AiPredictResponse.java` 这两个文件 ——
它们不是学生作业的产物，而是真实工程里最关键的交付物。契约定了，两边可以各自迭代，谁也不用等谁。

再往上一层，业界用专门的推理框架解决"多模型版本管理、动态批处理（把多个请求攒成一批一起推理，吞吐翻几倍）、多卡调度"这些问题：
**NVIDIA Triton Inference Server**、**TensorFlow Serving**、**KServe**。
本项目手写的 FastAPI 服务可以理解为这些框架的简化版。

#### 我们评估过的替代方案：Java 内嵌 ONNX 推理

**注意：Java 是能跑模型的**，说"Java 跑不了模型"不准确。
准确的说法是：**训练几乎只能在 Python 做，但推理 Java 完全可以。**

- **ONNX Runtime** 有官方 Java API，模型导出成 ONNX 后 Java 直接加载推理
- **DJL**（AWS 的 Deep Java Library）专门做这件事
- **TensorFlow Java** 也能加载模型

所以"必须用 Python"只在**训练阶段**成立。那为什么推理也不内嵌到 Java 里？这是一次有意识的取舍：

| 维度 | 拆成 Python 服务（**现方案**） | Java 内嵌 ONNX |
|---|---|---|
| 训练 | ✅ 本来就在 Python 生态 | ❌ 得另开一套 Python 训练完再导出 |
| 部署复杂度 | 两个进程，要管两个服务 | ✅ 一个进程 |
| 请求延迟 | 多一跳网络（本机约 1ms，可忽略） | ✅ 少一跳 |
| 模型迭代 | ✅ 重启 Python 服务即可，Java 不动 | ❌ 要重新打包整个 Java 应用 |
| 扩展到病虫害 | ✅ 加一个接口 | ❌ 每加一个都要动 Java 侧 |
| **YOLO 后处理** | ✅ Ultralytics 全包了 | ⚠️ **NMS、坐标还原、裁剪要自己在 Java 里重写** |

**最后一条是真正决定性的技术理由。** YOLO 的检测后处理不是"读个输出"那么简单 ——
非极大值抑制（NMS，压掉重复框）、锚点坐标还原、按框裁剪再喂给分类模型，
这一整套 Ultralytics 在 Python 里都封装好了。搬到 Java 要自己实现一遍，
不但工作量大，更危险的是**容易和训练时的行为不一致**，产生难以定位的精度下降。

**答辩/面试标准答法**（两层叠加，缺一不可）：

> 业务层用 Java，是因为团队技术栈和生态成熟度；模型单独做服务化部署是行业标准做法。
> 而且我们的模型**需要 GPU、需要独立迭代、后续还要扩展病虫害识别**，拆开之后
> Java 侧完全不感知模型变化。
> 我们也评估过 ONNX 内嵌方案，但 **YOLO 的后处理在 Java 里要重写**，
> 还容易和训练时不一致，收益不如成本。

**为什么不能只说"因为我要找 Java 实习"：** 那是真实动机，但在面试里是**减分**的 ——
它听起来像"为了让简历好看硬套了个 Java"，而不是"为解决技术问题做的选择"。
技术理由必须能独立站住，个人动机可以叠加在后面。

### 2. 为什么要 Redis？

不是为了"简历上好看"，三个真实用途：

- **会话与 token 管理**：JWT 是无状态的，签出去就收不回。要支持"退出登录立即失效"，必须有个地方记录已作废的 token —— Redis 的 TTL 天然适合。
- **热点统计缓存**：看板上的"本周成熟度分布"每次都要扫全表聚合，很慢。这个结果几分钟内不变，缓存起来。
- **接口限流**：识别接口吃 GPU，一个用户狂刷会把服务打爆。用 Redis 计数做限流。

### 3. 为什么统一响应体 `R<T>`？

前端只按 `{code, message, data}` 解析一次，以后加接口不用改解析逻辑。**不这样会怎样：** 每个接口返回结构都不一样，前端写一堆 if。

### 4. 为什么第一步先不接数据库？

因为整个系统里**最不确定的一环是"Java 能不能顺利调通 Python"**（跨进程、跨语言、文件上传、编码）。先把这个验证了，再接数据库这种"确定性的体力活"。

**如果反过来先写数据库**：写完一堆 CRUD，最后发现调不通 AI 服务，前面全白做。

### ★ A1 为什么单独列出来

2026-09-26 的实测发现（见 [`TECH_DATA.md`](TECH_DATA.md)）：
**检测层在整树照片上只找到 2% 的果实**（2026-09-26 的历史值），因为训练集 92 张**全是未熟青果的近景大图**。
2026-09-27 补小目标数据后重测：整棵树提升到 **61 个框（约 30%）**，但**仍有约 70% 漏检**，负样本仍为 0。

这不是"补个数字"，是**补一个能力**。在它解决之前，"判断一整片林子的成熟度"这个说法撑不住。

**两条路，必须选一条**（详见 `TECH_DATA.md` 末尾）：
- **A. 补数据**（给整树/远景照片画框，几天工作量）
- **B. 把声称范围缩到"近景巡检"**（现在就能走通，且诚实）

### 明确"不做"的范围（防止烂尾）

「综合巡检」的完整设想包含病虫害识别，但**现阶段不做**。原因：

- 病虫害识别需要**重新采集和标注一整套数据**（本项目柿果数据集的原始图片已丢失，无法扩充）
- 一个做扎实的成熟度模块，价值高于三个都只有 demo 水平的模块

**答辩时这样说反而加分**："我们聚焦成熟度这一个高价值场景做深，病虫害是规划中的下一步 —— 技术上复用同一套两层架构，只需替换第 2 层模型。" 这体现了**工程判断力**，比堆功能更受评委认可。

## 五、数据模型（已实现）

> **⚠️ 本节 2026-10-05 重写过。** 原版（10-02 写的）是 `user / inspection / inspection_item` 三张表，
> 那是**在实地调研和老师谈话之前**设计的。后来定位变了，表也跟着变了。
> 现在的真实结构以 `persimmon/src/main/resources/db/schema.sql` 为准。

**三张表：**

```
region                      一个区域
├ id
├ name                      区域名，唯一
├ remark                    备注
└ create_time

capture                     一次采集（三张里长得最快的）
├ id
├ region_id        → region.id
├ captured_at               采集时刻
├ image_path                原图【相对】路径
├ count_unripe              四类果实的数量
├ count_turning             （不是"一个成熟度"字段 ——
├ count_coloring             一次采集会同时看到四类，
├ count_full                 存一个值根本表达不了）
├ detect_ms, classify_ms    两层耗时（诊断用）
└ create_time

notification                一条通知
├ id
├ region_id        → region.id
├ triggered_at              触发时刻
├ count_unripe / turning / coloring / full   触发【当时】的数量快照
├ message                   给用户看的一句话
├ is_read                   0=未读 1=已读
└ create_time
```

### 和原版比，改了什么、为什么

| 原版 | 现在 | 为什么改 |
|---|---|---|
| `user` 表 | **去掉** | 登录明确不做 |
| `inspection` | 改名 `capture` | 语义更准：一行 = 一次采集，不一定是"人巡检" |
| `device_note`（地块） | **提升成独立的 `region` 表** | 区域要能查、能统计，不是随手写的一行备注 |
| `fruit_count` 冗余字段 | **去掉** | 四个数量能加出来，**能算出来的不存** |
| `inspection_item`（每颗果一行） | **去掉** | 产品是**区域级**决策工具，不需要知道"第 37 号果在哪"。代价是放弃空间信息，可接受 |
| — | **新增 `notification`** | 老师提的"提醒"，而且它和"报警"不是一回事（天数尺度，用定时任务，不用 WebSocket） |

### 三个关键设计决定

**① 不建汇总表。** "某区域某天总共多少"用 `GROUP BY` 查出来，不单独存。
理由：数据量小、查询算出来的永远对、等真慢了再加。

**② 索引是联合的。** `capture` 上建 `(region_id, captured_at)`，
而不是两个单列索引 —— 最常见的查询是"某区域某段时间"，联合索引才用得上。
**没给成熟度建索引**：它只有 4 个值，区分度太低，建了也不走。

**③ `notification` 是事件流水，不是状态表。**
一旦生成就是历史事实，所以可以安全地存"当时"的数量快照。
**绝不能拿它当"当前成熟度"来查** —— 没超过阈值就没有通知，它根本没有"当前值"。

### ⚠️ 汇总时的一个坑

多组数据合并时，**先加数量再算比例，千万不要 `AVG(百分比)`**：

```
采集A：10 颗里 9 颗可采 → 90%
采集B：100 颗里 40 颗可采 → 40%

❌ 平均百分比： (90% + 40%) / 2      = 65%
✅ 先加后除：   (9 + 40) / (10 + 100) = 44.5%
```

样本量不一样，凭什么各占一半权重。
